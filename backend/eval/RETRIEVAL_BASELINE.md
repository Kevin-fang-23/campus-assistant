# 混合检索评测基线

> 数据集：`retrieval_set.json`（16 条语料 / 29 条查询，自带语料，离线可复现）
> 记录时间：2026-09-11
> 权重：`hybrid_weight_vector=0.2` / `hybrid_weight_bm25=0.8`（本次扫描实测最优）
> 复现命令：`python -m eval.run_retrieval_eval --embedding <local_hash|dashscope> [--sweep]`

## 一、三路对比

### 生产配置（dashscope 真实向量）

| 配置 | Recall@1 | Recall@3 | Recall@5 | MRR@5 | nDCG@5 |
|---|---|---|---|---|---|
| 仅向量 | 0.931 | 0.966 | 1.000 | 0.949 | 0.962 |
| 仅 BM25 | 0.966 | 1.000 | 1.000 | 0.977 | 0.978 |
| **混合 0.2:0.8** | **0.966** | **1.000** | **1.000** | **0.983** | **0.985** |

### 兜底配置（local_hash 本地哈希向量，无 Key 时）

| 配置 | Recall@1 | Recall@3 | Recall@5 | MRR@5 | nDCG@5 |
|---|---|---|---|---|---|
| 仅向量 | 0.724 | 0.862 | 0.897 | 0.796 | 0.816 |
| 仅 BM25 | 0.966 | 1.000 | 1.000 | 0.977 | 0.978 |
| **混合 0.2:0.8** | 0.897 | **1.000** | **1.000** | 0.943 | 0.952 |

**结论**：dashscope 下混合（0.983）> 仅 BM25（0.977）> 仅向量（0.949）——
混合超过任一单路，是设计意图成立的直接证据。
local_hash 下混合（0.943）低于仅 BM25（0.977），因为本地哈希向量本身噪声大，
掺进来反而拉低排序 —— 这也说明**兜底路径下更该依赖 BM25**。

## 二、权重扫描（dashscope，`--sweep`）

```
 w_vec  w_bm25 |  Recall@1  Recall@3    MRR@5   nDCG@5
   0.0     1.0 |     0.966     1.000    0.977    0.978
   0.1     0.9 |     0.966     1.000    0.977    0.979
   0.2     0.8 |     0.966     1.000    0.983    0.985   ← 默认取此
   0.3     0.7 |     0.931     1.000    0.966    0.972
   0.4     0.6 |     0.931     1.000    0.966    0.972
   0.5     0.5 |     0.931     1.000    0.966    0.972
   0.6     0.4 |     0.931     1.000    0.960    0.967
   0.7     0.3 |     0.966     1.000    0.977    0.980
   0.8     0.2 |     0.966     0.966    0.974    0.980
   0.9     0.1 |     0.966     0.966    0.974    0.980
   1.0     0.0 |     0.931     0.966    0.949    0.962
```

**怎么读这张表**：

- 曲线呈 **W 形**（0.0–0.2 与 0.7–0.9 是高地，0.3–0.6 是低谷），极差 3.4 个百分点。
  这种非单调形态在 29 条查询上是**噪声**，不宜当成"0.3 就是比 0.7 差"的结论。
- 但两端的定性方向是稳的：**BM25 偏重（低向量权重）整体优于向量偏重**，
  且两个极端（1.0:0.0 的 0.949）明显最差 —— 说明两路都用上才有价值。
- 因此默认取低向量端高地内的 **0.2:0.8**，而非刀尖上的单点。

## 三、两路互补性

dashscope 下：

```
仅 BM25 召回成功（向量漏掉）: 0 条
仅向量召回成功（BM25 漏掉）: 0 条
```

local_hash 下 BM25 补了 3 条向量的漏召：

```
· 二叉搜索树的作业      （字面精确："二叉搜索树"直接命中）
· 027-87654321          （精确电话号，哈希向量完全抓不到）
· 想听个 AI 方面的报告   （AI 为 ASCII 词，哈希向量丢掉了）
```

**这正印证了混合检索的动机**：校园场景里充斥课程名、房间号、电话、缩写这类精确串，
向量路对它们不可靠，BM25 一次命中。

## 四、⚠️ 已知局限（不要过度解读这些数字）

1. **语料只有 16 条**。真实库到上百条后，BM25 的字面碰撞会显著增多、区分度下降，
   而向量的相对价值上升 —— 届时应重跑 `--sweep` 重新定标，不要沿用 0.2:0.8。
2. **查询偏"词面密集"**。29 条里多数查询与目标通知共享实词（中文短查询的天然特点），
   这对 BM25 有利。已补 5 条语义改写型查询（"饭卡怎么没法在手机上充钱了"等）来平衡，
   但样本量仍偏小。
3. **单条语料对应单条查询**。没有覆盖"一个查询应对多条通知"的排序质量
   （仅 1 条 case 标了 2 个 expected）。
4. 评测是**离线、内存索引**，不覆盖真实链路上的 DB 查询与分页开销。
